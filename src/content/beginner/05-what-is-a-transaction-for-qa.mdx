<Callout type="info">
  In Web3 QA, a "transaction" is not just a button click. It's a multi-step lifecycle involving
  wallet confirmation, network propagation, mining/validation, and on-chain state changes.
</Callout>

<SectionTitle>Goal</SectionTitle>
Understand the transaction lifecycle and validate the correct UX + on-chain evidence at each phase.

<SectionTitle>Transaction Lifecycle (Simplified)</SectionTitle>

1. **User action**: Click "Swap / Stake / Mint / Send"
2. **Wallet prompt**: User confirms or rejects
3. **Broadcast**: Signed tx is sent to the network via RPC
4. **Pending**: Tx waits in mempool / queue
5. **Confirmed**: Tx included in a block (or finalized)
6. **State update**: Balances / positions / NFT ownership / logs updated

<SectionTitle>QA Checklist</SectionTitle>
<Checklist>
  <CheckItem>Wallet prompt appears quickly after user action (no dead-click feeling)</CheckItem>
  <CheckItem>User reject shows a clean message and resets loading state (no crash)</CheckItem>
  <CheckItem>When tx is submitted: show pending UI with tx hash + link to explorer (if available)</CheckItem>
  <CheckItem>Pending state handles slow confirmations (spinner + status text)</CheckItem>
  <CheckItem>On confirmation: UI updates balances/state and shows success toast</CheckItem>
  <CheckItem>On failure/revert: UI shows the reason when possible (or a clear generic error)</CheckItem>
  <CheckItem>No double-submission: button disables during pending, prevents duplicate clicks</CheckItem>
  <CheckItem>If user changes account/network mid-tx, the UI handles it gracefully</CheckItem>
</Checklist>

<SectionTitle>Manual Steps</SectionTitle>
<Steps>
  <Step>Connect wallet on a testnet (recommended) or a sandbox environment</Step>
  <Step>Trigger an action that sends a tx (e.g., a simple write action in your dApp)</Step>
  <Step>Reject the tx in MetaMask and verify UI recovers properly</Step>
  <Step>Submit the tx and observe the "pending" state</Step>
  <Step>Copy the tx hash and open it in a block explorer</Step>
  <Step>Wait for confirmation and verify the UI reflects the on-chain state change</Step>
</Steps>

<SectionTitle>What to Verify On-Chain</SectionTitle>

- **Tx status**: success vs failed
- **From/To**: sender and contract address
- **Method**: function called (decoded input if explorer supports it)
- **Events/logs**: emitted events match the UI expectation
- **State**: balances/positions changed as expected

<SectionTitle>Evidence to Capture</SectionTitle>

- Screenshot: wallet prompt
- Screenshot: pending UI + tx hash
- Explorer link: tx details (status, logs)
- Screenshot: success/failure message in UI

<SectionTitle>Done When</SectionTitle>

You can explain and validate:

- reject vs submit
- pending vs confirmed
- failed/reverted tx UX + evidence
